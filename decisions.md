# Decisions log

Things I noticed about the data, and what I decided to do about them.

| # | What I found | Decision | Why |
|---|---|---|---|
| 1 | Each request can only return a limited number of days of data. | Download data one calendar month at a time (12 files). | One file per month stays under the limit and is easy to check and re-run. |
| 2 | Each monthly file also returns the half-hour that ends at its start time, so the last half-hour of each month (23:30 UTC) appears in two adjacent files: 11 duplicates. The forecast values are identical in both copies. | Keep one row per `from_utc`, taking the copy from the earlier file. Same rule per `from_utc` + `fuel_type` in `stg_generation_mix`. | Duplicates would double-count those half-hours in averages. Because both copies match, which one I keep doesn't change any number; picking the earlier file just makes the rule deterministic. |
| 3 | 26 of the year's 17,520 half-hours are missing from the API (0.15%): 12-13 Jan (17), 10-11 Aug (8) and the last half-hour of 31 Dec (1). | Leave the gaps as they are. Don't fill them in. | Too few to change any average: every cell in the profile mart is still based on at least 11 half-hours. Filling them in would mean inventing forecasts the API never made. |
| 4 | The API returns all times in UTC (ending in `Z`). From late March to late October London is on BST (UTC+1), so 18:00 in London is 17:00 UTC. | Keep `from_utc` (and `to_utc`) as the key, and add `from_london_time` using `AT TIME ZONE 'Europe/London'`. All seasons, weekdays and times of day in the marts are taken from London time. | The user plugs in by the clock on their wall, not by UTC. Without conversion, every summer result would be one hour off. UTC is kept as the unique key because London time repeats an hour when the clocks go back (26 Oct 2025). |
| 5 | The generation-mix percentages for a half-hour don't always add up to exactly 100 (observed 99.8 to 100.2). Each of the 9 fuel shares is rounded to 1 decimal place. | Accept the data as it is. The check flags any half-hour whose total is more than 0.5 away from 100 (expect 0 rows). | The largest possible rounding error is 9 x 0.05 = 0.45, so anything within 0.5 is rounding, and anything outside it would be a real problem. |
